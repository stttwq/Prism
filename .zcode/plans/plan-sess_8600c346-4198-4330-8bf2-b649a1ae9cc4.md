# G7: `ext:` 与 `path:` 查询过滤 — 实施计划

## 概述

在 Top-K 前增加可组合的 `ext:` / `path:` 过滤。broker 负责解析 query 文本为结构化 FilterSet，indexer 在候选进入 Top-K 堆前应用过滤。不新增协议通道——复用 G1 预留、G3 已使用的 `filters` 可选字段。

## 架构决策

**解析在 broker 侧**（非 WPF），与 design.md 一致。WPF 不复制解析逻辑，只负责展示输入和接收结果。`>` 前缀解析（G5）已在前端做，但那只是单字符判断；ext/path 解析涉及引号、OR/AND 语义和回退规则，复杂度不适合前端复制。

**FilterSet 与 SearchFilter 复用同一 `filters` 字段**。现有 `SearchFilter { field, value }` 中 field 只允许 `exclude_path`。新增 `ext` 和 `path` 两个 field 值，不新增枚举类型——保持 wire format 向后兼容。

## 步骤 1：表驱动测试先行（Rust）

在 `ipc.rs` 新增 `mod query_parser_tests`，用测试固定解析契约：

- `report ext:pdf` → name_query="report", filters=[{ext, pdf}]
- `design ext:md,pdf path:"Project Docs"` → name_query="design", ext OR md|pdf, path AND
- `ext:.pdf` → 前导点被规范化掉，ext=pdf
- `EXT:PDF` → 大小写不敏感，ext=pdf
- `ext:` → 空值，回退为普通文本 "ext:"
- `path:"unterminated` → 未闭合引号，回退为普通文本
- `foo:bar` → 未知前缀，按普通文本处理
- 多个 ext → AND 语义（每个 ext filter 独立）
- 重复 ext:pdf ext:pdf → 两个相同 filter，AND 后仍只匹配 pdf

## 步骤 2：broker parser + 有界 FilterSet（Rust, `ipc.rs`）

新增 `parse_query(raw: &str) -> (String, Vec<SearchFilter>)` 函数：

- 单次有限状态扫描，识别未转义的 `ext:` 和 `path:` 前缀
- `ext:` 值用逗号分隔取 OR；每个逗号值规范化（去前导点、lowercase）
- `path:` 值需要双引号包裹含空格的值；未闭合引号回退为普通文本
- 未识别前缀、不完整 token、空值均按普通文本保留（不静默丢失输入）
- 输出 `name_query`（剩余普通 token 拼接）+ 结构化 filters
- 有界：filter 数量 ≤ MAX_FILTERS(32)，单值长度 ≤ MAX_FILTER_VALUE_BYTES(1024)

在 `search_service` 入口调用 `parse_query`，将解析出的 filters 合并到请求已有的 filters（G3 exclude_path）中，然后传给 indexer。

## 步骤 3：协议扩展 + 版本兼容（`indexer_ipc.rs`）

修改 `validate_search_request`：
- 新增 `ext` 和 `path` 为合法 field 值
- `ext` 值：非空、无控制字符、长度 ≤ 1024
- `path` 值：非空、无控制字符、长度 ≤ 1024（不要求绝对路径——是子串匹配）

新增 `ext_filters(filters) -> Vec<String>` 和 `path_filters(filters) -> Vec<String>` 辅助函数（与 `exclusion_paths` 同模式）。

## 步骤 4：indexer 候选过滤（`hierarchy.rs` + `indexer_runtime.rs`）

在 `search_volumes` 中，候选通过名称匹配后、进入 Top-K 堆前，增加 ext 和 path 过滤：

- **ext 过滤**（低成本，先用）：从候选 name 取扩展名（最后一个 `.` 后部分，lowercase），检查是否在 ext 集合中。目录无扩展名，除非 ext 匹配空值（本任务不支持空值匹配，目录直接跳过 ext 过滤）。
- **path 过滤**（需构造路径）：对通过 ext 的候选，用 `volume.path_for(record)` 构造完整路径，做 Windows 不区分大小写的字面子串匹配。构造次数计入 `path_constructions` 统计。

修改 `search_volumes` 签名，增加 `exts: &[String]` 和 `paths: &[String]` 参数。`indexer_runtime.rs::search` 提取 ext/path filters 并传入。

**关键正确性保证**：过滤在 Top-K 堆之前，不在之后。`is_truncated` 只针对全部过滤后的候选。path 构造只对通过 ext+name 匹配的候选执行（先低成本过滤，再高成本路径构造），但 path 过滤仍必须在取 max 之前。

## 步骤 5：broker 有过滤器时排除应用/窗口/网页（`ipc.rs`）

PRD 要求：有过滤器时只返回文件/文件夹，不混入应用、窗口或网页结果。

在 `search_service` 中：如果解析出 ext 或 path filter，跳过 websearch 匹配、apps 搜索和 window mode 路径，只走 indexer 文件搜索。

## 步骤 6：前端请求身份与缓存失效（C#, `SearchViewModel.cs` + `SearchAbstractions.cs`）

**不在 WPF 复制解析逻辑。** WPF 把原始 query 文本发给 broker，broker 解析后 echo 回的结构化结果已经反映了过滤。

但缓存键需要变化：
- `SearchContext` 已有 `Filters` 字段和 `IsEquivalentTo` 比较
- 当 query 中包含 `ext:` / `path:` 时，缓存行为天然安全：不同 filter 的 query 文本不同，prefix cache 的 `StartsWith` 检查不会跨 filter 命中
- 但需确认：`TryFilterCompleteCache` 的 prefix 过滤逻辑在 query 含 `ext:` 时仍然正确——因为 broker echo 的 query 是 name_query（已剥离 filter token），而前端比较用的是原始 query

**修正**：前端发原始 query，broker echo 回 name_query。这会导致 `QueryMatchesResponse` 比较失败。解决方案：broker 在 `Response::Results.query` 中 echo **原始 query**（不剥离），与 G5 window 模式的处理方式一致（window 模式也是前端 strip `>` 后发给 broker，但 broker echo 的是 stripped query）。

重新审视：现有 G5 模式前端发 stripped query，broker echo stripped query，前端用 stripped query 比较。G7 同理——**前端发原始 query，broker parse 后发 name_query 给 indexer，但 echo 原始 query 回前端**。这样 `QueryMatchesResponse` 和 prefix cache 逻辑不需要改动。

实际上更简单：broker 在 `search_service` 中解析后，用 name_query 做索引搜索，但在 Response 中 echo 原始 `query` 参数。这已经是现有模式——`query` 参数就是原始输入。

## 步骤 7：测试覆盖

### Rust 测试（`ipc.rs` + `hierarchy.rs` + `indexer_ipc.rs`）

1. **Parser 表驱动测试**（步骤 1 已述）
2. **Top-K 前过滤测试**：构造语料（100 个 .txt + 100 个 .pdf），`ext:pdf max=8` 返回 8 个全 .pdf，证明过滤后仍返回足额
3. **root + ext + path 组合**：构造 root 下的文件，证明三重 AND 过滤后仍返回足额 `max=8`
4. **有过滤器时不返回应用/网页**：mock apps + websearch，验证 ext 过滤时被跳过
5. **协议兼容测试**：旧 reader（无 ext/path field）仍正常解码；新 field 不破坏已有 exclude_path 语义
6. **未知/不完整 token 回退**：`foo:bar`、`ext:`、`path:"unclosed` 全部按普通文本处理

### C# 测试

7. **缓存失效**：ext:pdf 和 ext:md 的 query 不互相命中 prefix cache
8. **迟到响应**：filter 变化后旧 filter 响应不覆盖新结果（已有 `_searchSeq` 机制覆盖，确认测试）
