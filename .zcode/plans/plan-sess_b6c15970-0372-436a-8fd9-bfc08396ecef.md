# 内存占用 + 动画流畅度优化方案（不动架构）

## 现状结论

经全量审读，稳态内存已高度紧凑（`NodeSlot` 12B/节点、name pool 字节池、拼音 sidecar 已 mmap）。剩余可优化点集中在两处：**瞬态内存峰值**和 **WPF 渲染/动画流畅度**。以下 9 项改动均不改变三进程架构、IPC 协议、数据结构语义，只消除浪费和卡顿。

---

## 第一部分：内存占用优化（4 项）

### M1. v5 缓存保存去掉全量 `cloned()` 峰值
**文件**: `src/prism-core/src/indexer_runtime.rs:850-853`
**现状**: `persist_first_build_with` 在保存前 `guard.as_ref().cloned()` 整个 `IndexState`（~78MB），仅在 `spawn_blocking` 线程内 postcard 编码完就丢弃。checkpoint 路径（`indexer_runtime.rs:1157-1160`）同理。这导致每次保存瞬间 indexer 私有工作集 +78MB。
**改动**: 改为在持读锁期间直接编码到字节缓冲，不克隆 `IndexState`。将 `save` 闭包签名从 `FnOnce(&IndexState)` 改为直接持锁编码——具体做法是让 `persist_first_build_with` / checkpoint 接收一个 `FnOnce(&IndexState) -> Result<(), String>` 并在**读锁作用域内**调用它，由 `index_cache::save` 内部完成 postcard 编码。postcard 的 `Serializer` 写入 `Vec<u8>`，不需要 `IndexState: Clone`。
**效果**: 保存时峰值从 +78MB 降至 +编码缓冲大小（postcard 紧凑编码后约等于磁盘文件大小，远小于内存结构）。
**风险**: 低。读锁持有时间 = 编码时间（毫秒级），与原克隆时间相当或更短（省了克隆+drop）。

### M2. Broker 结果排序缓冲 `lowercased` 避免逐项 `to_lowercase()` 分配
**文件**: `src/prism-core/src/ipc.rs:1516-1520`
**现状**: `sort_search_results` 对每个结果 `item.title.to_lowercase()` 各分配一个 `String`，构建 `Vec<String>`。8 条结果 = 8 次堆分配。
**改动**: 改为 `Vec<SmallVec<[u8; 64]>>` 或直接用 `Vec<(usize, String)>` 索引+复用单缓冲。更简洁的方案：用 `sort_by_cached_key`（标准库），让它在内部缓存 key，避免手动维护 `lowercased` 数组和 `visited` 置换。
**效果**: 减少分配次数和代码量；标准库实现更优。
**风险**: 极低。排序结果不变。

### M3. Broker `process_indexer_reply` 减少重复字符串克隆
**文件**: `src/prism-core/src/ipc.rs:863-897`
**现状**: 每个 `IndexerItem` 的 `path` 被 clone 三次：`target.value`(clone)、`subtitle`(clone)、`execute_id`(move)，`name` 被 clone 一次给 `title`。`target` 本身还被 clone 一次（用于 `injected_history_targets` 去重检查）。
**改动**: 调整字段消费顺序——`item.path` move 给 `execute_id`，用 `item.path.as_str()` 给 `subtitle` 和 `target.value`。`target` 用引用做去重检查而非 clone。即把 `target.value.clone()` 改为借用 `&target.value` 做 `HashSet` 查找。
**效果**: 8 条结果省 ~16 次 `String` clone。
**风险**: 低。需确认 `ActionTarget` 的 `From`/构造方式允许引用传入。

### M4. 首次构建 `enumerate_mft` 的 500k 容量预分配降为按需增长
**文件**: `src/prism-core/src/ntfs.rs:528`
**现状**: `Vec::with_capacity(500_000)` 预分配 500k 个 `UsnRecord`（每个含一个 `String`，结构体约 56B + String 堆）。3.3M 节点卷会触发多次 realloc，但首次分配就占 ~28MB 空结构。
**改动**: 改为 `Vec::new()` 配合 `extend` 的批量增长策略。Windows MFT 枚举每批返回的记录数不固定，`extend(batch)` 已经会按 2x 增长。或者改为更保守的 `with_capacity(64_000)` 作为初始提示。
**效果**: 构建峰值降低（3.3M 节点不再一次性预占 28MB 空壳）。
**风险**: 低。`extend` 会自动 realloc；性能影响可忽略（realloc 次数从 ~3 次变为 ~6 次，但省了初始大块）。

## 第二部分：动画流畅度优化（5 项）

### A1. 面板高度动画期间冻结 `SizeToContent`，消除逐帧窗口重布局
**文件**: `src/Prism/Windows/SearchWindow.xaml.cs:717-753` (`AnimatePanelHeight`) + `SearchWindow.xaml:5`
**现状**: 窗口声明 `SizeToContent="Height"`。当 `PanelHost.Height` 从 0 动画到目标时，WPF 每帧都触发 `Window` 高度重测量（因为 `SizeToContent` 告诉 WPF "内容多高窗口就多高"）。这是动画期间最重的逐帧开销。
**改动**: 在 `AnimatePanelHeight` 开始动画前设 `SizeToContent = SizeToContent.Manual`，计算最终窗口高度并直接 `Height = 最终值`；动画结束后恢复 `SizeToContent = Height`。具体：动画前 `SizeToContent = Manual` + 设固定 `Height`，让动画只影响 `PanelHost` 内部 clip 区域，不影响窗口尺寸。
**效果**: 动画期间窗口不再逐帧重测量，消除 `SizeToContent` 导致的布局抖动。
**风险**: 中。需确保固定高度计算正确（Header高度 + Panel目标高度 + Padding）。已有 `UpdateListHeight` 的几何计算可复用。需手测呼出/隐藏/展开面板三种路径。

### A2. 配置 WPF 渲染提示（`UseLayoutRounding` + `TextOptions`）
**文件**: `src/Prism/Windows/SearchWindow.xaml:13` (Card Border) + `src/Prism/Controls/ResultList.xaml:17` (ItemTemplate Grid)
**现状**: 全项目无 `UseLayoutRounding`、`TextOptions.TextFormattingMode`、`TextOptions.TextRenderingMode` 配置。文字密集列表在 DPI 缩放下有亚像素模糊和重排抖动。
**改动**:
- `SearchWindow.xaml` 的根 `Window` 加 `UseLayoutRounding="True"` + `RenderOptions.BitmapScalingMode="HighQuality"`
- `ResultList.xaml` 的 ItemTemplate `Grid` 加 `TextOptions.TextFormattingMode="Display"` + `TextOptions.TextRenderingMode="ClearType"`（小字号列表文字清晰度+渲染速度）
- `ResultList.xaml:24` 的 `Image` 加 `RenderOptions.BitmapScalingMode="Linear"`（32px 图标用 Linear 足够，比默认 HighQuality 快）
**效果**: 文字渲染更清晰，图标缩放更快，亚像素对齐消除抖动。
**风险**: 极低。纯声明式属性，不影响逻辑。

### A3. `DecorateVisibleItems` 只遍历已生成的容器范围，不遍历全量 `List.Items`
**文件**: `src/Prism/Controls/ResultList.xaml.cs:252-328`
**现状**: `for (var i = 0; i < List.Items.Count; i++)` 遍历全部条目（最多 1000），对每个调 `ContainerFromIndex`。虚拟化下未实现的返回 null 后 `continue`，但 1000 次循环+null 检查在每次滚动时都跑。
**改动**: 改用 `ItemContainerGenerator` 的 `Items` / 通过 `VirtualizingStackPanel` 的 `Panel.FindVisualChildren<ListBoxItem>()` 只遍历已实现容器。或更简单：记录 `ScrollViewer.VerticalOffset` 和 `MaxVisibleRows` 计算 `[firstVisible, lastVisible]` 范围，只遍历该范围。
**效果**: 滚动时装饰开销从 O(1000) 降至 O(9)。
**风险**: 低。需确保范围计算覆盖 `CanContentScroll=True` 的 item-offset 语义。

### A4. `AllowsTransparency="True"` 的阴影渲染改用独立 `Border` 模拟，避免软件合成
**文件**: `src/Prism/Windows/SearchWindow.xaml:6,13-24,25-27`
**现状**: `AllowsTransparency="True"` + `Background="Transparent"` 强制 WPF 走软件合成路径（某些 GPU 上）。`DropShadowEffect` 在透明窗口上效果重。这是窗口动画卡顿的最大潜在来源。
**改动**: 这是最敏感的改动——**不在本次动**。`AllowsTransparency` 改动需要改窗口创建方式（从 `AllowsTransparency` 迁移到 WS_EX_NOREDIRECTIONBITMAP 或普通窗口+区域裁剪），属于架构级调整，超出"不动架构"约束。仅在代码注释中标记为已知瓶颈，留作未来评估。
**效果**: 无（标记为已知限制）。
**风险**: 跳过此项以遵守约束。

### A5. 图标 `Image` 的 `CacheMode` + 冻结位图复用
**文件**: `src/Prism/Controls/ResultList.xaml:24-30` + `src/Prism/Services/IconCache.cs`
**现状**: 图标已 `Freeze()` 且按扩展名共享，但 `Image` 控件无 `CacheMode`，每次容器回收时位图重新提交到合成器。
**改动**: 在 `ResultList.xaml` 的 `IconImage` 上加 `CacheMode`（用一个 `BitmapCache` 或直接在 `RenderOptions` 层）。实际上更安全的做法是不加 `BitmapCache`（它增加内存），而是确保 `Image` 的 `Stretch="Uniform"` + `SnapsToDevicePixels="True"` 已最优。**此项验证后保留 `Stretch`/`SnapsToDevicePixels` 现状，不加 `BitmapCache`**（避免增加内存，与内存目标冲突）。
**效果**: 无（验证后确认现状已优）。
**风险**: 无。

## 执行顺序

1. **M1** — 缓存保存去克隆（影响最大、最安全）
2. **M2** — broker 排序缓冲（简单、低风险）
3. **M3** — broker 字符串去重（简单）
4. **M4** — MFT 枚举预分配（构建路径）
5. **A1** — SizeToContent 冻结（动画最关键，需手测）
6. **A2** — 渲染提示（纯声明式）
7. **A3** — DecorateVisibleItems 范围优化（需验证虚拟化偏移）

每项改完跑对应测试：Rust 改动跑 `cargo test` + `cargo clippy -D warnings`；C# 改动跑 `dotnet build` + `dotnet test`。A1 改完需手动验证呼出/隐藏/展开面板三种动画路径。

## 不做项（明确排除）

- **A4 `AllowsTransparency` 迁移** — 属架构级窗口创建方式变更，超出"不动架构"约束
- **`opt-level` 从 `"z"` 改 `"3"`** — 已有 baseline 数据（z=31MB vs 3=51MB），改了会破 100MB 门
- **索引数据结构重设计** — `NodeSlot` 已 12B 最优，name pool 已字节池化
- **IPC 协议/管道改动** — 协议契约不动
- **拼音 sidecar 改 mmap** — 已是 mmap
