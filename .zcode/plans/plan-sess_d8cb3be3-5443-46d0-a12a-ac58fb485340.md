# Prism 安装后三个问题修复计划

## 问题诊断结论

### 问题1：高强度搜索导致搜索失败 + 搜索「知乎」出现「之火」
**根因（字节级已验证）：** `SuggestionService.cs:106` 对所有联想 HTTP 响应一律用 `Encoding.UTF8.GetString(resp.Body)` 解码。但百度联想 API (`suggestion.baidu.com/su`) 返回的是 **GBK 编码**（`Content-Type: text/javascript; charset=gbk`）。GBK 字节被当作 UTF-8 解读后产生替换字符和杂散码点，「之火」就是「知乎」的 GBK 字节被误读为 UTF-8 的具体表现。Bing 和 Google 返回 UTF-8，不受影响。

**搜索失败部分：** 高强度输入时，每次搜索 broker 都会向 indexer 发起一次全新的命名管道连接（`indexer_client.rs:128` `connect()`，2 秒超时，5 次重试各 20ms）。indexer 只有 4 个监听槽（`PIPE_LISTENERS = 4`），高速连续搜索时连接可能排队甚至超时，返回 `indexer service request timed out`。这与 Trellis 活跃任务 `08-07-prism-ipc-resilience`（缺陷 A: ERROR_PIPE_BUSY）相关。

### 问题2：已运行一个 Prism 时点击图标仍启动第二个
**根因：** Prism.exe（C# WPF）完全没有单实例机制——没有 `CreateMutexW`、没有命名管道服务器做实例探测。`App.OnStartup`（`App.xaml.cs:45`）无条件构造所有服务并 `TryStartBackendAsync()`。第二个 Prism.exe 会启动第二个 prism-core.exe（后者的 `first_pipe_instance` 会失败并退出，但第二个 Prism GUI 仍带工作正常的后端连接第一个 broker 继续运行，形成两个托盘图标、两个热键注册）。

### 问题3：退出后重开，prism-core 未运行
**根因：** `PipeClient` 没有 watchdog——`EnsureBackendRunning()` 仅在 `StartAsync()` 启动时调用一次，且只检查本进程持有的 `_backend` 子进程是否已退出。没有 `EnableRaisingEvents`、没有 `Exited` 事件、没有后台健康检查。当 Prism 退出时 `OnExit` → `Dispose()` 会 `Kill(entireProcessTree: true)` 杀掉 core，这是正确的；但重开后如果 core 因任何原因（如退出时管道残留、竞态）启动失败，没有任何恢复机制。`SearchViewModel` 在搜索失败时有一个 `await _pipe.StartAsync()` 重连尝试（`SearchViewModel.cs:823`），但首次搜索前用户会先看到「搜索失败」。

## 修复方案

### 修复1：百度联想 GBK 编码（问题1 — 乱码）

**文件：** `src/Prism/Services/SuggestionService.cs`

**方案：** 让 `SystemHttpTransport` 把响应声明的 charset 带出来，`SuggestionService` 按声明解码；同时给百度 adapter 的 URL 加 `ie=utf-8` 参数请求 UTF-8 响应（双保险）。

1. **扩展 `HttpResponse` record**，增加 `string? CharSet` 字段（`SuggestionService.cs:24`）：
   ```csharp
   public sealed record HttpResponse(int StatusCategory, byte[] Body, string? CharSet);
   ```

2. **`SystemHttpTransport.GetAsync`** 读取 `Content-Type` 的 charset（`SuggestionService.cs:49-61`）：
   ```csharp
   var charset = resp.Content.Headers.ContentType?.CharSet;
   // ...读取 body...
   return new HttpResponse(category, buf[..read], charset);
   ```

3. **`SuggestionService.GetSuggestionsAsync`** 按 charset 解码，回退 UTF-8（`SuggestionService.cs:106`）：
   ```csharp
   var encoding = TryResolveEncoding(resp.CharSet) ?? Encoding.UTF8;
   var text = encoding.GetString(resp.Body);
   ```
   新增私有方法 `TryResolveEncoding(string?)`，处理 `"gbk"`/`"gb2312"` → `Encoding.GetEncoding("gbk")`（.NET 内置支持），无效/未知回退 `null`。

4. **百度 adapter URL 加 `ie=utf-8`**（`SuggestionService.cs:195-196`），请求百度返回 UTF-8：
   ```csharp
   "https://suggestion.baidu.com/su?wd=" + ... + "&action=opensearch&ie=utf-8"
   ```
   即使百度忽略该参数，步骤 3 的 charset 解码仍能正确处理 GBK。

5. **更新所有 `FakeHttpTransport` / `SlowHttpTransport`** 构造以适配新 record（测试文件 `G8WebEnhancementsTests.cs:237-267`）。

6. **新增测试** `Baidu_GBK_Body_Decoded_Correctly`：构造一个 GBK 字节 body + `CharSet="gbk"` 的 fake transport，断言解析出正确中文联想。

**关于搜索失败（超时）：** 这属于 `08-07-prism-ipc-resilience` 任务范围（indexer 管道饱和）。本次不做管道连接池化大改，但在 broker 端做一个轻量改进：当 indexer 返回超时错误时，`search_service` 已经把它降级为 `index_error` 返回（`ipc.rs:959-971`），前端会显示 `index_error`。这是合理降级。本次主要修复乱码这个确定性 bug。

### 修复2：单实例 + 激活已有实例（问题2）

**文件：** `src/Prism/App.xaml.cs`、`src/Prism/Services/SingleInstance.cs`（新建）、`src/Prism/Prism.csproj`

**方案：** 命名互斥锁（`CreateMutexW`）+ 命名管道让第二个实例通知第一个实例唤出窗口。

1. **新建 `src/Prism/Services/SingleInstance.cs`**：
   - P/Invoke `CreateMutexW`（`kernel32.dll`），互斥名 `Local\PrismSingleInstance`。
   - `TryAcquire()` 返回 bool；`GetLastError() == ERROR_ALREADY_EXISTS` 表示已有实例。
   - 若已有实例，通过命名管道客户端向 `\\.\pipe\prism-foreground` 发送一行 `show` 指令，然后返回 false。
   - 持有互斥锁的进程在 `OnStartup` 中启动一个 `NamedPipeServerStream` 监听 `\\.\pipe\prism-foreground`，收到 `show` 时 `Dispatcher.BeginInvoke` → `ToggleSearchWindow()`。

2. **`App.OnStartup` 顶部**（`App.xaml.cs:45`，在 `base.OnStartup` 之后、任何服务构造之前）：
   ```csharp
   _singleInstance = new SingleInstance();
   if (!_singleInstance.TryAcquire())
   {
       _singleInstance.SignalExistingInstance(); // 发 show 指令
       Shutdown();
       return;
   }
   _singleInstance.StartForegroundListener(Dispatcher, ToggleSearchWindow);
   ```
   关键：必须在 `TryStartBackendAsync()`（line 106）之前 return，防止启动第二个 core。

3. **`App.OnExit`**（`App.xaml.cs:301`）：`_singleInstance?.Dispose()` 释放互斥锁和监听器。

4. **`Prism.csproj`**：无需改自定义 Main——在 `OnStartup` 中做互斥锁足够早（WPF 视觉树尚未创建，`ShutdownMode = OnExplicitShutdown` + `Shutdown()` 不会弹窗）。

5. **新增测试**：`SingleInstance` 的管道信号逻辑可拆出静态方法测试（发送/解析 `show` 指令）。

### 修复3：prism-core watchdog 守护（问题3）

**文件：** `src/Prism/Services/PipeClient.cs`

**方案：** 在 `PipeClient` 内增加后台 watchdog，定期 ping 后端，连续失败则重连/重启 core。

1. **`PipeClient` 增加 watchdog 字段与启动逻辑**：
   ```csharp
   private Timer? _watchdog;
   private int _consecutiveFailures;
   ```
   在 `StartAsync` 连接成功后启动 `PeriodicTimer`（每 15 秒 ping 一次）。使用 `System.Threading.Timer`（非 UI 线程，避免 Dispatcher 依赖）。

2. **watchdog 回调**：
   - `PingAsync` 成功 → `_consecutiveFailures = 0`。
   - `PingAsync` 失败 → `_consecutiveFailures++`；达到阈值（2 次）时调用 `EnsureBackendRunning()` 重新拉起 core，再 `ConnectAsync`。
   - 所有操作在 `_ioLock` 保护下进行，避免与搜索请求竞态。
   - 连接恢复后通过事件/回调通知 `SearchViewModel` 刷新 `_state.IsBackendConnected`。

3. **`EnsureBackendRunning` 强化**（`PipeClient.cs:440`）：当前仅检查 `_backend.HasExited`。增加：若 `_backend` 为 null 或已退出，重新 `Process.Start`。watchdog 调用此方法。

4. **`Dispose`**（`PipeClient.cs:527`）：`_watchdog?.Dispose()` 停止定时器。

5. **事件通知**：`PipeClient` 暴露 `event Action<bool>? ConnectionChanged`，watchdog 在连接状态变化时触发，`App.TryStartBackendAsync` 订阅它更新 `_state.IsBackendConnected`。
