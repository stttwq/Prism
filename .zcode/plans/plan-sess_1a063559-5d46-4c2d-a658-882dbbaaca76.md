三个问题各自独立，改动文件不重叠，可并行实施后一次提交。

### R-A1：世代长轮询协议版本不匹配（1 vs 2）

**根因**：`IndexerGenerationClient.cs:22` 写死 `ProtocolVersion = 1`，服务端 `lib.rs:42` 要求 `INDEXER_PROTOCOL = 2`。握手必然失败，前端永远走 3 秒超时退化路径，文件操作后结果不即时刷新。

**改动**（两步）：

**第 1 步——立即修复**（1 行）：
- `src/Prism/Services/IndexerGenerationClient.cs:22`：`ProtocolVersion` 从 `1` 改为 `2`
- 核对 hello/status/wait_generation 请求字段与 `indexer_ipc.rs` 的 `IndexerRequest` 枚举逐一对应。已确认：
  - hello：`{ type: "hello", protocol: N }` ✓
  - status：`{ type: "status" }` ✓
  - wait_generation：`{ type: "wait_generation", after: N, timeout_ms: N }` ✓
- C# 侧加注释指向 `lib.rs:42` 的 `INDEXER_PROTOCOL` 作为"单一真源"

**第 2 步——结构性修复**（让以后版本不匹配不再静默降级）：
- Rust 侧 `indexer_runtime.rs:1507-1516`：把不匹配时的泛化 `Error { message: "incompatible or missing hello" }` 改为 `Error { message: "protocol_mismatch: server=2 client=X" }`（不改 `IndexerResponse` 枚举形状，只在 message 里带结构化前缀——避免协议变体膨胀）
- C# 侧 `IndexerGenerationClient.cs:105`：识别 `protocol_mismatch` 前缀，日志输出明确诊断信息（而非把完整异常吞掉只留 `ex.Message`）
- Rust 单测：在 `indexer_runtime.rs` 现有测试块尾部加测试——用 protocol=1 的 hello 连 mock 连接，断言收到 error 且 message 含 `protocol_mismatch`

**验证**：
- `cargo test`（含新测试）
- `dotnet test`（现有测试全绿）
- 手动：重命名一个文件后搜索结果在 1 秒内刷新（而非固定等 3 秒）

### R-B1：拼音重建在读锁内做全索引遍历 + fsync

**根因**：`rebuild_pinyin_from_live()`（`indexer_runtime.rs:326-340`）在 `self.index.read()` 内调用 `rebuild_pinyin()`，后者做全节点遍历 + `sidecar.save()`（含 fsync）。百万级中文文件下持读锁数秒~数十秒，阻塞 USN 写者和搜索读者。

**对照正确模式**：同文件 `persist_first_build_with`（1016 行）和 `checkpoint` 本体（1343 行）都是"读锁内 clone、放锁后 save"。`load_pinyin_outside_lock_force`（229 行）也是"读锁内取 identity、放锁后 load"。

**改动**（`src/prism-core/src/indexer_runtime.rs`，方法 `rebuild_pinyin_from_live`）：

把当前：
```
fn rebuild_pinyin_from_live(&self) {
    let data_dir = ...;
    if let Ok(index) = self.index.read() {
        if let Some(index) = index.as_ref() {
            self.rebuild_pinyin(index, &data_dir);  // 全遍历+save 在锁内！
        }
    }
}
```

改为：
```
fn rebuild_pinyin_from_live(&self) {
    let data_dir = ...;
    // 读锁内只 clone 快照，立刻放锁。
    let snapshot = {
        let Ok(guard) = self.index.read() else { return; };
        let Some(index) = guard.as_ref() else { return; };
        index.clone()  // 纯 memcpy，毫秒级
    };
    // 锁外做全遍历 + save + load 校验。
    self.rebuild_pinyin(&snapshot, &data_dir);
}
```

`rebuild_pinyin(&self, index: &IndexState, data_dir: &Path)` 签名不变——它接收 `&IndexState`，clone 出来的快照满足。`PinyinSidecar::build(index)` 遍历快照、`save()` 落盘、`load()` 校验，全部在锁外完成。

**关键安全检查**：
- `checkpoint` 调用 `rebuild_pinyin_from_live` 时（1354 行），已经在 1343 行 clone 了一份 `snapshot`。改后 `rebuild_pinyin_from_live` 内部会再 clone 一次。这多一次 clone（毫秒级 memcpy）不影响正确性——pinyin sidecar 的 identity/delta 对账机制（`PinyinSidecar::load` 校验 `index_identity`）保证装载的 sidecar 与当前 live index 对齐。如果 clone 期间 index 变了，sidecar 的 identity 不匹配，下次搜索会用 literal-only 结果，maintenance loop 检测到 `pinyin_needs_rebuild` 会重试。这与现有行为一致。

**新增 Rust 单测**：在 `indexer_runtime.rs` 测试块尾部加测试——启动一个线程调 `rebuild_pinyin_from_live`，同时另一个线程能在 <100ms 内拿到 `self.index.write()`。

**验证**：
- `cargo test`（pinyin_sidecar 与 indexer_runtime 现有测试全绿 + 新测试）
- `cargo clippy`

### C-D1：无全局异常兜底

**根因**：`App.xaml.cs` 的 `OnStartup` 没有注册任何全局异常处理器。任何 UI 线程未捕获异常或后台 `async void` 异常都会让进程无声消失。

**改动**（`src/Prism/App.xaml.cs`）：

在 `OnStartup` 开头（`base.OnStartup(e)` 之后）注册三个钩子：

1. **`DispatcherUnhandledException`**：记日志，对可恢复异常 `e.Handled = true`（进程不退出）
2. **`TaskScheduler.UnobservedTaskException`**：记日志，`e.SetObserved()`（防止 .NET 杀进程）
3. **`AppDomain.CurrentDomain.UnhandledException`**：记日志（无法阻止退出，但留遗言）

日志写入 `%LOCALAPPDATA%\Prism\logs\frontend.log`，简单 append + 10MB 截断。用现有 `Log` 方法扩展——加一个 `LogException(Exception ex)` 重载，写到文件。不加新依赖。

具体实现：
```
// 在 OnStartup 的 base.OnStartup(e) 之后：
DispatcherUnhandledException += OnDispatcherUnhandledException;
TaskScheduler.UnobservedTaskException += OnUnobservedTaskException;
AppDomain.CurrentDomain.UnhandledException += OnDomainUnhandledException;
```

三个处理方法各自 try/catch 包裹（异常处理器的异常不能再抛）。

日志文件方法：
```
private static void LogToFile(string msg)
{
    try
    {
        var dir = Path.Combine(
            Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
            "Prism", "logs");
        Directory.CreateDirectory(dir);
        var path = Path.Combine(dir, "frontend.log");
        var info = new FileInfo(path);
        if (info.Exists && info.Length > 10 * 1024 * 1024)
            File.Delete(path);
        File.AppendAllText(path,
            $"{DateTime.Now:yyyy-MM-dd HH:mm:ss.fff} {msg}\r\n");
    }
    catch { /* 日志不能反过来杀进程 */ }
}
```

`LogException(Exception ex)` 调用 `LogToFile`，输出异常类型、消息、堆栈。

**不影响现有功能**：
- 只在异常发生时介入，正常执行路径零改动
- `e.Handled = true` 只对 `DispatcherUnhandledException` 用——这意味着 UI 线程异常不再杀进程，而是记日志后继续运行。如果异常导致状态损坏，用户会看到 UI 可能不正常，但至少有日志可查。比无声消失好。
- 不改变任何现有 `async void` 的逻辑，只是补了兜底

**验证**：
- `dotnet build` + `dotnet test`
- 手动：用一个临时按钮抛异常，确认进程不退、日志有记录
