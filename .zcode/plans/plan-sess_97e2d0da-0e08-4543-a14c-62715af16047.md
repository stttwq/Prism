# 第四批修复实施计划（S3 + B4 + M7 + A4 + WPF 四小项）

7 个小项，每项独立可回退，全部为"加保护/加过渡"性质，不改任何现有功能语义。

---

## Rust 侧（2 项）

### 1. S3：窗口枚举移入 spawn_blocking

**问题**：`search_service` 的窗口模式分支直接在 tokio worker 上跑 `EnumWindows`（`GetWindowTextW` 对挂死窗口无限阻塞），broker 只有 2 个 worker，一次卡死堵住半个后台。

**改动**（`ipc.rs:973-979`）：照抄同函数里 `history_file_candidates` 的既有模式——克隆三个 `Arc`（SnapshotStore/HistoryStore/Preferences，已核实均 `Send+Sync`）+ owned query 进闭包：
```rust
if mode == SearchMode::Window {
    let (windows2, history2, pref2) = (windows.clone(), history.clone(), preferences.clone());
    let query_owned = query.to_string();
    let entries = tokio::task::spawn_blocking(move || {
        window_search(&query_owned, max, &windows2, &history2, &pref2)
    }).await.unwrap_or_default();
    return window_results(query, entries, history);
}
```
COM 公寓（`CoInitializeEx`）在阻塞线程上初始化/释放是安全的（每次枚举自包含）。**范围刻意收窄**：只动枚举路径；`ResolveWindow`/`RecordWindowSwitch` 的单窗口探针保留现状（单窗口、Enter 路径已有 8 秒超时兜底，重排它风险大于收益，记录为已知残留）。

### 2. M7：入站管道行长上限（1MB）

**问题**：broker 与 indexer 的连接读循环用 `next_line()` 无上限累积——任意本地进程连上灌一行超长数据即可撑爆内存。

**改动**（`ipc.rs:353-416` 读循环、`indexer_runtime.rs:1391-1471` 读循环）：
- 把 `BufReader::lines()` 换成逐行 `(&mut reader).take(MAX_LINE+1).read_until(b'\n', &mut buf)`；
- 超 1MB：broker 回一条 `Response::Error("请求超长")` 后断开；indexer 直接断开（走既有 disconnect 日志）；
- 其余语义逐项保留：EOF 断开、空行跳过、UTF-8 错误/解析错误回错误响应且连接保持、`\r\n`/trim 处理与 `lines()` 行为对齐（现有 trim 兜底）；
- 常规请求实为 KB 级，1MB 上限对合法流量零影响；出站方向（响应）不动。
- **新增测试**（两侧各一）：接测试管道后写 2MB 无换行数据 → 断言收到错误响应/连接关闭。

## WPF 侧（5 项）

### 3. B4：多显示器呼出定位

**问题**：`PositionWindow` 用 `SystemParameters.WorkArea`（主屏），副屏工作时呼出跳回主屏。

**改动**（`ForegroundInterop.cs` + `SearchWindow.xaml.cs`）：
- `ForegroundInterop` 新增 `GetWorkAreaForWindow(IntPtr)`：`MonitorFromWindow(MONITOR_DEFAULTTONEAREST)` → `GetMonitorInfoW` 取 `rcWork` → `GetDpiForMonitor`（Shcore）换算回 DIP——**混合 DPI 显示器下不会偏移**；任一步失败回退现有 `SystemParameters.WorkArea`（行为=现状）。
- `ShowAndFocus` 把已捕获的 `foreground` 传给 `PositionWindow`，在前台窗口所在显示器居中、顶部 25%。
- 主屏行为与现在完全一致（同一显示器时结果相同）。

### 4. A4：三处视觉过渡 + Divider 淡入

**设计要点**（规避 WPF 多触发器动画冲突的经典坑）：
- **选中/悬停背景过渡**：`Styles.xaml` 的 `ResultListBoxStyle` 与 `ActionPanel.xaml` 内联模板（两处同样改）改为**双层高亮**——`HighlightSelected`（`IsSelected` 驱动，0↔1）与 `HighlightHover`（`IsMouseOver` 驱动，0↔0.55）两个 Border 叠放，各自由唯一触发器持有，100ms `DoubleAnimation`。每个属性单一写入者，不存在触发器退出互相覆盖的闪烁。背景仍引 `BgItemSelected` 令牌，主题切换正常。现视觉测试（WebIconFlicker 等）将实际构建新模板，是现成的回归网。
- **ScopeChip 出现动画**：`SearchHeader.SetScope` 在"隐藏→可见"跃迁时 120ms 淡入 + 左移 8px 入场（单属性单动画，直接 BeginAnimation）。已知限制如实声明：输入框的横向位置仍会瞬移（彻底消除需重排布局，不做）。
- **PinButton 旋转动画**：`UpdateVisual` 保留单个 `RotateTransform`，`IsPinned` 切换时 `DoubleAnimation(to, 150ms)`（省略 From = 从当前动画值平滑续接）。
- **Divider 淡入**：`ApplyState` 把 Divider 从隐藏变可见时 100ms 淡入（隐藏仍瞬时收起）。

### 5. WPF-M1：broker 重启时释放旧 Process 对象

`PipeClient.EnsureBackendRunning`：`Process.Start` 赋值前 `try { _backend?.Dispose(); } catch`。watchdog 15 秒周期重拉场景下不再累积进程句柄。

### 6. WPF-S7：单实例监听加固 + 热键安装失败可见

- `SingleInstance.ListenLoop`：管道构造加 `PipeOptions.FirstPipeInstance`（注释本就声称独占，此前实际没传）；`catch` 分支加 `await Task.Delay(1s, ct)`——构造持续失败时不再 100% 空转烧核（取消令牌驱动，正常路径零延迟）。
- `HotkeyService.InstallLowLevelHook`：`SetWindowsHookEx` 返回 `IntPtr.Zero` 时 `Debug.WriteLine` 记录"双击 Ctrl 将不可用"——行为不变（双击 Ctrl 本就是兜底模式），但从静默死亡变为可诊断。

### 7. WPF-M3：JobObject 限制设置失败可见

`JobObjectGuard` 构造：检查 `SetInformationJobObject` 返回值，失败时 `Debug.WriteLine` 记录 Win32 错误码（提示"孤儿进程保护未生效"）。行为不变——失败时仍继续 Assign 尝试，最坏等于现状。

## 风险控制

- S3 闭包只进 owned/Arc 数据，无生命周期陷阱；unwrap_or_default 兜 JoinError；
- M7 逐行替换读循环，正常路径（KB 级行）逐字节等价；两个新测试钉住超限行为；
- B4 带 DPI 换算 + 全链路回退到现状值，主屏场景结果不变；
- A4 双层高亮是单写入者设计，杜绝触发器互踩；现有视觉测试守容器/图标零回归；
- WPF 三小项全部"失败可诊断化"，不改成功路径行为。
