# Prism 内容搜索方案建议

> 依据:`PRISM-CONTENT-SEARCH-EXPLORATION-2026-08-21.md` 的探讨与调研,结合
> Prism 现有架构(root_scope/查询过滤/逐卷发布/USN)与用户画像
> (内容搜索非必须、分门别类记得文件夹、反感重、安静且能成长)给出的判定。
> 日期:2026-08-21。

## 一句话结论

**做「过滤先行的 SIMD 定向现扫」,零常驻索引。** 不做全量倒排,不做记忆点/
分词/TF-IDF,布隆过滤器留作实测不够快后的优化层。Everything 用现扫、
ripgrep 证明现扫可以快——Prism 后端是 Rust,这条路是"复用最大、代价最小、
可逆"的那条:不满意随时删,不留常驻债。

## 方案形态(第一期)

### 触发语法:content: 前缀,过滤先行

- 查询语法对齐 Everything:`报告 content:甲方违约` —— content: 之前的部分
  先走现有文件名搜索管道(Top-K、ext:/path: 过滤、排除表全部照常),把候选集
  缩到最小;content: 之后的部分才是正文词,只对已缩小的候选扫正文。
- `content:` 单独出现(无前置词)= 全范围正文搜索,此时套用「内容搜索范围」
  (见下),而非全盘。
- 正文词按空白切分多词 AND——复用 NameTerms 式的查询层切法,**不做中文分词**:
  中文按连续 UTF-8 字节串匹配(ripgrep 同语义),多词需同时命中最多个词。

### 范围:用户文件域,按目录位置划

- 硬排除:`C:\Windows`、`C:\Program Files*`、`C:\$Recycle.Bin`、
  `C:\System Volume Information`、`C:\Recovery`。
- 灰色地带(AppData/ProgramData)**默认排除**,设置页「内容搜索范围」可开——
  复用现有 ExcludedPaths 机制加一份独立的 content 侧默认表,不动文件名搜索
  的全盘语义。
- 按目录位置划界,不按文件来源(USN 创建记录)——探讨文档里"来源划界"的
  复杂度换不来对等价值,弃。

### 引擎:broker 侧现扫,ripgrep 同源 crate

- 依赖 `memchr`(SIMD 字面量匹配)+`regex`(惰性 DFA),都是 ripgrep 同源、
  成熟维护的 crate;不自己写匹配内核,不引 grep 整包。
- 字面量优先:提取正文词的最长字面量片段先 SIMD 搜,命中位置再验证整词。
- 每文件纪律:大小上限(建议 10MB,超出跳过并在状态行说明)、单文件读取
  用带缓冲的顺序读(**大量小文件不用 mmap**——ripgrep 基准:小文件 mmap 慢
  约 5 倍)、整块 buffer 搜不逐行。
- **单并发纪律**:同一时刻只允许一个 content 搜索在跑(Everything 同款),
  新请求取消旧的——复用现有 searchCts 取消管道。
- **流式呈现**:边扫边发布命中行,复用 broker 现有逐卷/分批发佈机制与前端
  的 seq 守卫;扫完置完成态,超时预算(建议 8s,与 REQUEST_BUDGET 对齐)到点
  即止,状态行显示"已扫 N 文件/共约 M"。

### 类型:第一期纯文本

txt / md / json / xml / csv / ini / log / 代码源文件(按扩展名白名单)。
- 二进制嗅探:前 8KB 含 NUL 即跳过(避免乱码输出)。
- Office(docx/xlsx=压缩 XML)与 PDF 留第二期走 Windows iFilter 系统组件,
  没注册 iFilter 的类型降级跳过——复用系统能力,不引解析库。

### 结果呈现

- content 命中行作为独立结果档:标题=文件名,副标题=命中行上下文截断+
  高亮 span,kind="content"(前端新档,复用现有行模板与 MatchSpans 机制)。
- 与文件名结果并行合流时按文件去重(content 命中优先保留,带命中摘要)。

## 为什么不是另外两条路

- **全量倒排(DocFetcher/Recoll 型)**:常驻内存几百 MB 起,为"非必须"功能
  破 ≤100MB 三进程门,撞用户反感 Listary 的那个点。Listary 自己都把内容搜索
  推给伴生产品——信号很清楚:内容搜索与启动器是两个产品形态,塞一起必拖累。
- **记忆点/布隆过滤器**:探讨文档已论证——"记忆点"需中文分词+TF-IDF(重投入
  且分词库是新依赖);"高频词"不等于记忆点。布隆过滤器是有界代价的合理优化,
  但它的优势前提是"反复搜同一批文件",而内容搜索定位是非必须低频——低频
  场景下过滤器构建维护成本可能比省下的扫描还多。**留触发器:现扫实测确认
  慢、且用户真实反复使用后,再加布隆层**(每文件词集布隆,USN 增量维护,
  懒构建:只在文件第二次被 content 扫到时才建)。

## 增量节奏

1. **第一步:语法+纯文本现扫+流式**(上述第一期全量)。验证两件事:排除系统
   目录后用户文件域的现扫速度;用户是否真的用。
2. **第二步(视实测)**:iFilter 支撑 Office/PDF;扫描预算/文件上限调参。
3. **触发器不动**:布隆层、中文分词、"文件来源划界"——等真实需求出现。

## 待用户拍板

- 灰色地带(AppData/ProgramData)默认关——确认。
- 文件大小上限 10MB/搜索总预算 8s——首发值,可调。
- 是否需要 `content:` 也支持正则(建议首发不做,字面量+多词 AND 够用且防
  灾难回溯)。
