## 一、跑的不是你改的代码（最大的时间黑洞）

### 现象

改代码 → 编译通过 → 行为完全不变。反复几轮，怀疑代码逻辑、怀疑协议、
怀疑操作系统，最后发现改动根本没进到运行中的进程。

### 根因：同时存在三份二进制

```
src/prism-core/target/debug/prism-core.exe      8月5日  <- 前端实际加载的
src/prism-core/target/release/prism-core.exe    8月6日  <- 我一直在编的
C:\Program Files\Prism\prism-core.exe           8月1日  <- 安装的
```

三处都「存在」，没有任何一处报错。具体成因有三个，各自都足以独立致命：

**1. 前端的 broker 发现逻辑写死了 debug 优先**

`PipeClient.LocateBackend` 里是 `foreach (var cfg in new[] { "debug", "release" })`，
且只判 `File.Exists`。只要 `target\debug` 里躺着一个陈旧 exe，无论 release
多新都会被忽略。**Release 构建的前端去加载 Debug 构建的后端**，这个组合本身
就不该发生。

**2. cargo/dotnet 的「静默 no-op」**

`Finished in 0.37s` / `所有项目均是最新的` + 退出码 0 —— 看起来是成功，
实际什么都没做，产物还是旧的。我被这个骗了至少三次。

**3. 服务安装步骤是手工的**

`Stop-Service` 返回后进程可能还没退，文件仍被锁，`Copy-Item` 静默失败。
结果安装目录里 broker 是 8月1日、indexer 是 8月5日，混装状态。

### 已经做的防护

`scripts/prism-build.ps1` 把构建到安装串成一步，并且：

- 装完用 **SHA-256** 逐个比对安装字节与构建字节，不一致就 `DRIFT DETECTED` + 退出码 1
- 校验产物时间戳不早于源码最新改动，早了就报「build silently did nothing」
- 释放文件锁移到**构建之前**（Prism 在跑时会锁死自己的输出）
- 握手回传 `build_id`（`0.1.0+release.<源码mtime>`），运行中的进程能自报身份

### 下次的检查顺序

行为不符预期时，**先证明跑的是你改的代码**，再怀疑逻辑：

```powershell
.\scripts\prism-build.ps1 -VerifyOnly    # 不改任何东西，只查漂移
```

配合 `build_id`：连上 broker 发 `{"type":"hello","protocol":1}`，
回包里的 `build_id` 应该和你刚编的源码 mtime 对得上。

### 一个放大伤害的设计

`root` 是**可选协议字段**，设计意图是「新旧版本可独立发布，旧服务收到也不报错」。
代价是版本不匹配时**不会报错，只会静默退回旧行为**。E1 就是这样：范围标签是
前端自己算出来显示的，看着正常；过滤在服务端压根没发生。

协议向后兼容不等于可观测。加可选字段时，考虑让服务端在收到不认识的字段时
至少回一个诊断位，否则排查只能靠猜。

## 二、环境陷阱（这台机器特有，但很容易再遇到）

### PowerShell 5.1 在中文 locale 下按 GBK 读无 BOM 的 UTF-8

这是本次最阴的一个。写了带中文注释的 `.ps1`，运行时报的是
**语法错误**（引号失配、`}` 意外），而且报错行号指向的位置和真正的问题无关。
我为此反复改了四五个脚本的括号，全是白费。

**规则**：辅助脚本一律用**纯 ASCII**。需要中文说明就写进 `.md`，不要写进 `.ps1`。
所有 `artifacts/g4-test-build/*.ps1` 和 `scripts/*.ps1` 都遵守这条，文件头有注明。

### Git 的 coreutils `link` 会被 rustc 当链接器用

`/usr/bin/link`（Git for Windows 自带的 coreutils 工具）在 PATH 里排在
MSVC 的 `link.exe` 前面。rustc 调用它，报：

```
link: extra operand '...libwindows_sys-....rlib'
Try 'link --help' for more information.
```

**关键陷阱**：纯库构建不需要链接，所以 `cargo build` 对 lib 目标一直成功。
只有产出 `.exe` 时才炸。这让它能潜伏很久——本次会话里前面几十次构建都正常，
直到某次触及链接才暴露。

**解法**：`source scripts/msvc-env.sh`（bash）或 `prism-build.ps1` 的
`Initialize-Toolchain`（PowerShell）。两者都自动发现 MSVC 版本和 SDK 版本，
不写死路径。

### Directory Opus 接管了默认文件管理器

`explorer.exe <路径>` 和 `explorer.exe shell:MyComputerFolder` 打开的**都是
Opus 的 Lister**，不是真资源管理器。我用这两条命令反复自动化测 E3，
`CabinetWClass` 窗口永远找不到，白跑好几轮，直到用户指出来。

**测真资源管理器只能用 Win+E**（或者 `EnumWindows` 找 `CabinetWClass`）。

附带：Opus 会把自己的 Lister 注册进 `ShellWindows`，但不支持那套 COM 属性，
读 `HWND`/`Document` 都抛 `COMException`。代码靠 catch 兜住了，行为没错，
但这解释了为什么 `ShellWindows.Count` 有五六条却只有一两条是真 Explorer。

### PowerShell 7 的模块目录会遮蔽 5.1 的内置命令

装了 PowerShell 7 之后，它的 Modules 目录被注入 `PSModulePath`，
导致 5.1 会话里 `Get-FileHash` 报「无法将...识别为 cmdlet」。
哈希校验整段失效，而机器本身是健康的。

**解法**：`prism-build.ps1` 显式 `Import-Module Microsoft.PowerShell.Utility`，
并保留 `certutil` 作为回退。

### bash 里 `python` 不存在，只有 `py`

`python --version` 静默无输出（不是报错），`py --version` 才有。
用 `python - <<'PY'` 写的 heredoc 会静默什么都不做——**不报错、退出码 0**。
一律用 `py`。

### 重装系统会抹掉整条工具链

本次中途用户重装了系统，MSVC、.NET SDK、`C:\Program Files\Prism`、
`PrismIndexer` 服务、`C:\ProgramData\Prism` 索引数据全没了。
`prism-build.ps1` 原本假设「装过一次」，目录缺失就直接报错——
已加 `-Bootstrap`：目录缺失就建、服务缺失就用 `sc.exe create` 注册。

### 代码搜索工具会返回过期索引，报出早已删除的文件

2026-08-09 文档审计时，AI 助手的 `grep_search`（跨文件搜索）声称
`src/prism-core/src/index.rs` 仍然存在，还多报了两个从未存在过的
`index.rs.bak` / `index.rs.bak2`。

实际情况：该文件在 G3 的 `23dbad4` 就已删除。三种方式交叉验证一致——
`ls` 列不出、`find src -name 'index.rs*'` 零结果、`git ls-files` 计数 0、
`git log --diff-filter=D` 指向删除提交。所以工具读的是一份**过期索引快照**，
不是当前工作树。

同一轮里另一个表现：`grep_search` 只回一个文件名、不给任何匹配行，
看起来像"匹配到了但内容为空"，实际是没真查。

**后果**：如果采信，就会把「index.rs 还在」这类假事实写进文档——而那次任务
的目的恰恰是清掉文档里的假事实，等于反向污染。

**判据**：凡是「某文件/某符号已删除」这类结论，不要只信搜索工具，
用 `find` + `git ls-files` 复核。两者不一致时**以文件系统和 git 为准**。

配套坑：同一轮 bash 工具整段静默过一次，连结尾的 `echo probe-ok` 都没输出。
这类"零结果"是**工具失败**，不是"查无此项"——判断方法是在命令末尾接一个
必然有输出的 `echo`，它也没出来就说明整条命令没跑。

### PowerShell 的 ordered hashtable vs PSCustomObject

同一份样本，在本进程内是 `[ordered]@{}`（hashtable），从 JSONL 读回来是
`PSCustomObject`。**`$obj.PSObject.Properties['key']` 读不到 hashtable 的键**，
静默返回 `$null`，不报错。

后果：基准脚本第一轮把每一行的 `root` 都记成了 `(global)`，
数据看着完整但字段全丢。已抽出 `Get-SampleField` 统一处理两种形态。

配套坑：`Set-StrictMode -Version Latest` 下访问不存在的属性会**抛异常**，
所以读之前必须先探测存在性。

## 三、验证方法上的错误（比环境坑更值得记）

### 单测全绿 ≠ 格式正确

O1（Opus 无法识别目录）的根因是 `dopusrt /info paths` 输出的是 **XML**，
而解析器在按行找盘符开头的路径，恒得 0 条。

**而单测是绿的** —— 因为喂给它的夹具是我们自己编的纯文本格式，Opus 从不产出
那种格式。测试验证的是「解析器能解析我们想象的格式」，不是「能解析真实输出」。

**教训**：涉及外部程序输出的解析，夹具必须来自**真实抓包**。这次是先跑
`dopusrt /info` 把 XML 存下来，再据此改夹具。同类隐患：任何 `/info`、
`--json`、COM 属性的返回格式，都不能凭文档或想象写夹具。

### 「修完 0 错误」是不可证伪的

E3 修完后洪峰探针 150 轮零失败，看着像修好了。用 `dist/` 里那个**未修复**的
旧二进制做 A/B 对照 —— **它在更猛的洪峰下同样零失败**。

也就是说我的探针复现不了原始故障，「修完没错」这个观察根本不能支持
「修复有效」这个结论。

**教训**：声称修好一个偶发缺陷之前，必须先用**未修复的版本**在同样的负载下
复现出故障。做不到复现，就只能说「代码缺陷已修，因果链未证明」——
这正是 `08-07-prism-ipc-resilience` 现在的措辞，任务保持 `in_progress`。

### 合成负载 ≠ 真实负载

我用 4 个 writer 制造 USN 洪峰，做到 **5800 世代/秒**，远超故障当天的
**340 世代/秒**，仍然复现不了。差异不在 USN 速率，而在两处：

1. **CPU 未饱和**。当天是 Windows 更新在解压安装，CPU 和磁盘同时打满。
   合成洪峰只产 USN 记录，CPU 有大量余量 —— 而工作线程饥饿恰恰需要 CPU 竞争。
2. **索引规模差一半**。当天 `memory_bytes` 是 171MB；重装后重建只有 66MB。
   索引小 → 搜索快 → 持锁短 → 竞争弱。

**教训**：复现并发缺陷时，先想清楚「压力的哪个维度才是触发条件」。
把某一个容易造的维度推到极限，不代表复现了故障。

### 规范措辞过窄会放跑违规代码

`quality-guidelines.md` 原文禁的是「Blocking index/app **scan** on the async
pipe runtime thread」——只提扫描。而 `IndexerRequest::Status` 取的是
`index.read()`，不是扫描。读规范的人完全可以认为「`status()` 没问题」。

**教训**：写禁令要按**机制**描述，不要按**症状**描述。已改为「任何取
index/pinyin/history 锁」，并写清后果链。

## 四、我犯的流程错误

这一节是给我自己的。上面的坑是环境和方法，这节是明确可避免的判断失误。

### 删掉了唯一一份干净数据

第一轮 root 基准实际**采集成功了**——完整的查询/max 矩阵，每组 30 个暖样本
（当时输出报 720 个暖样本；该 artifact 已被我删除，此数字无法从磁盘复核，
仅凭当时的终端输出）。但那轮的聚合有 bug（每行都记成 `(global)`），
我修完 bug 后直接 `rm -rf artifacts/bench/g4-root-20260807` 清目录重跑。

原始 JSONL 里**每条样本都带 `root` 和完整 workload**，完全可以离线重新聚合，
不必重采。删掉之后机器环境变了（Windows 更新开始跑、随后又重装系统），
就再也采不到干净数据了。

**规则**：修聚合/汇总逻辑时，原始数据是不可再生的。**先复制走，或者直接对
已有原始数据重跑聚合**，绝不清目录重采。

### 采信了 5 天前的记忆，没有验证

我依据一条记忆（「G9 源码丢失，重编译会把服务降级」）在给用户的测试文档里
写了「不要重新编译」。而那条记忆早已过期——源码在 `bc01766` 里已经恢复。

**这条错误指引直接导致 E1 失败**：用户按文档用了不含 G4 代码的旧服务去测。

系统提示里明确说过记忆是时间点快照、引用前要核实。我没做。
**规则**：记忆里任何关于「文件是否存在 / 代码是否可用 / 某路径在哪」的断言，
引用前必须用一条命令核实。核实成本远低于错误指引的代价。

### 没先问环境就开始自动化

Opus 接管默认文件管理器这件事，用户机器上的既有配置，我完全可以在
动手前问一句。结果是反复用 `explorer.exe` 自动化了好几轮，全部无效。

**规则**：涉及「调起某个系统程序」的自动化，先确认那个程序在这台机器上
是不是被替换过。一句话的确认，省几十分钟。

### 写了一个会卡住所有人的测试

为缺陷 A 补回归测试时，第二版走真实 `handle_connection` 路径，
用 `worker_threads = 1` —— 服务端任务和客户端读取争同一个线程，**必然死锁**。
`cargo test` 直接挂住，需要杀进程才能恢复。

**规则**：写涉及 IPC 往返的测试，客户端和服务端必须能并行调度。
`worker_threads = 1` 只适合单向、无往返的场景。提交前用 `timeout` 兜一层：
`timeout 180 cargo test ...`，挂住能自己退出而不是卡死终端。

### 在 PowerShell 语法上反复试错，太晚才换工具

GBK 那个坑导致脚本报语法错，我改了四五轮括号和引号。正确做法是在第二次
失败时就停下来质疑「是不是根本不是语法问题」，或者直接换工具——
C# 探针（`TabProbe`）一次就跑通了，而且能拿到 PowerShell 拿不到的 COM 数据。

**规则**：同一类错误改两次没进展，停下来换工具或换路径，不要接着试。

## 五、下次开工前的检查清单

按顺序做，每条都是这次踩过的：

```powershell
# 1. 工具链齐不齐（重装系统后必查）
.\scripts\prism-build.ps1 -VerifyOnly

# 2. 跑的是不是我改的代码
#    上面那条会报 DRIFT DETECTED；也可以查 build_id
```

```bash
# 3. bash 侧的工具链
source scripts/msvc-env.sh    # MSVC link.exe + dotnet 都会就位
py --version                  # 不是 python
```

测试相关：

- 要测**真资源管理器**：Win+E，不要 `explorer.exe <path>`（会开 Opus）
- 写 `.ps1`：**纯 ASCII**，中文写进 `.md`
- 写 IPC 测试：不要 `worker_threads = 1`；用 `timeout` 兜一层
- 改聚合逻辑：先备份原始数据，不要清目录重采
- 采信记忆里的路径/文件断言：先用一条命令核实

基准采集（`Invoke-SearchBaseline.ps1` 会在索引世代移动时中止，这是**正确**的）：

- 需要安静机器：`SetupHost` 等更新进程结束、世代稳定、Prism 前端与 Opus 关闭
- 索引要长回完整规模（`memory_bytes` ≥ 150MB），否则和历史数据不可比
- `Invoke-RootScopeComparison.ps1` 是配对对照工具，容忍世代移动，
  但**不能替代正式基准**；看结论前先核对 `sample_count` 与 `errors`
