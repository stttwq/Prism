## 背景:Prism 站在哪

用户对三款对标产品的反感很明确:
- **Listary** — 内存重、会员功能反感
- **Everything** — 界面简陋、不能自动隐藏、呼出麻烦
- **Prism 现状** — 恰好站在这三家的中间空地:≤100MB 三进程总和(比 Listary 单进程还轻)、开源免费无会员、深浅色跟随系统+动画、双击 Ctrl 呼出顺滑、失焦即隐

**差异化标签不是"功能更多",是"安静且能成长"。** 新增能力守住"薄"就有未来,做厚了就变成自己反感的东西。

## 结构洞察(比功能清单更耐用)

这些不绑死任何一个功能,但会长期起作用——动手做任何具体方向时,这些判断能少走弯路:

1. **差异化是"安静且能成长",不是"功能多"**。Listary 重 Everything 丑,Prism 站中间。新增能力守住"薄"。
2. **别名/note/标签背后是同一张表**——`路径 → 用户标注`。将来真做,共用一个标注层挂 history 旁,不各建各的。免费的结构红利。
3. **"搜到 → 处理"闭环已满**(打开目录/复制路径/压缩/重命名全齐)。扩展系统的价值在跳出"文件"这个框,去碰和文件无关的事(note/ocr/calc)。
4. **内置 handler 路线够用**,直到某天想加的能力太重不适合塞主进程,那才是拆外部进程的自然时机。不做 webview/SDK/插件市场。
5. **"先做内置再观察"**:预览/note/ocr 先用最朴素方式(handler 函数),做三四个后共同模式浮出来再抽象成正式注册表。现在凭空设计规范大概率漏掉真实需求。
6. **三进程落点**:前缀命令类 handler(note/ocr)前端自己闭环不增 broker 负担;结果动作类(预览)碰文件走 broker 现有通道。broker 不因此变重,守住薄。

## 设想方向(未排先后,未定方向)

### A. 自定义文件关键词(别名系统)

多词系统:一个文件可绑多个词(weixin.exe 绑 wx 和微信),`路径 → [词列表]`,持久化挂 history 旁。

- **精确触发,独立通道**:打 wx 精确命中别名,打 weix 走正常字面搜索,各走各的不合并。别名是独立召回快车道。
- **冲突仲裁**:同词多文件都在别名通道内,用 frecency 排序,最近常用哪个哪个赢。冷启动期按设置时间倒序。
- **别名命中写同一条 history**:最终用户"打开 weixin.exe"不因怎么搜到而有区别,frecency 该反映真实使用频率。别名只管召回入口,history 记结果动作。
- **和字面搜索总排序**:别名命中给高档(接近整名精确 class),让正常 class 体系打破平局。
- **路径失效**:移动/删除时悬空,检测存在性静默降级(项目里 history stale paths 教训现成)。
- **双入口**:右键结果行"设置别名"(搜到顺手设) + 设置界面(统一看、批量删)。高频文件少数,不搞批量导入导出。
- **设置界面隐性价值**:别名变可见资产,避免命令式设完就忘的通病。

**潜力**:别名做好后部分替代扩展系统——"高频文件快速到它"这个最大痛点,别名比 handler 更自然(在搜索流里不用学新前缀)。真正需要扩展系统的是和文件无关的能力(note/ocr/calc)。

### B. 预览 Quick Look

选中结果按空格弹浮层显示文件内容。和 macOS Quick Look 同心智。

- **渲染分层**:
  - 文本(txt/md/json/xml/代码)— WPF 原生,几乎零成本
  - 图片(png/jpg/gif)— WPF Image,零成本
  - PDF — 需渲染器,Windows 10+ 内置但 API 不干净,或引小库,可选
  - Office — 硬,靠互操作,重且不稳,跳过
- **交互坑**:空格只在"结果行已选中、焦点在列表"时触发,不能在搜索框打字时截获(否则打 `note ` 按空格弹预览)。
- **handler 契约**:拿选中行文件路径 + 探测类型,返回可渲染内容。浮层瞬态不占列表布局。
- **IO 落点**:大文件读内容走 broker(已有 pipe 通道),前端不直接碰磁盘 IO。

### C. note 便签

完全跳出文件范畴的纯用户数据。`note xxx` 存,`notes` 列。验证"前缀命令"这条扩展路。

- 数据跟 history 放一起(broker 持有),前端只读写,前端重启数据不丢。轻量 KV 挂现有 history 旁。
- frecency 引擎可复用(最近笔记置顶)。

### D. ocr 截屏识字

截屏选区 → Windows 原生 OCR(WinRT `Windows.Media.Ocr`,系统内置、免费、本地、快)→ 文本进搜索框。验证"触发外部能力再回填"这条路。

- 截屏在前端(拿屏幕 DC),OCR 调 WinRT 在前端,不碰 broker。
- **区分**:这是 OCR(提取文字),不是多模态大模型理解图片内容。后者牵出密钥管理/隐私/费用/网络依赖,违背"薄",先不碰。

### E. calc 计算器

输入算式直接出结果。最小(几十行),验证"即时计算无文件"这条路。

### F. 命令面板化(战略级,最大想象空间)

双击 Ctrl 呼出框这个交互范式天然不限于文件搜索。Raycast/Alfred/PowerToys Run/VSCode Command Palette 都是"一个框接住一切"。Prism 底座已往这走:web 关键词(`g/b/bi`)、应用搜索、动作面板。差的是把"搜文件"心智扩成"搜一切可执行的"。

具体增量:计算、系统动作(休眠/设置页)、颜色转换等。单看都小,叠加起来 Prism 从"文件搜索器"变"统一入口"。这是对标从 Listary 转向 Raycast 的战略级选择。风险是摊子易铺大,守"文件搜索仍是第一公民"。

### G. 标签/收藏系统

文件搜索解"我知道文件名大概叫什么",解不了"我知道有这么个文件但想不起名字"("王总上个月发我的合同")。给文件打自定义标签按语义召回,数据量轻(几千条顶天),挂 history 旁,frecency 引擎复用。

Everything/Listary 没做透这片高地——它们做"匹配文件名",标签做"匹配用户意图"。

### H. 磁盘分析/重复文件查找(性价比最稳)

MFT 全盘索引已在跑,文件名+大小+路径全在内存。数据现成可低成本衍生:
- 磁盘空间分析(对标 WizTree/TreeSize):按目录树聚合"哪个文件夹占 50G"
- 重复文件查找:按大小分组→同大小哈希比对
- 大文件定位:按大小排序找占空间大户

不碰搜索核心,横向扩产品面。几乎零额外索引成本,但 UI 投入大(树形图/treemap 可视化)。

## 已确定的原则

- **排序:P1/P2(多音字+全路径拼音)先收口对标 Listary 搜索维度**,扩展系统在其后。但当前设想阶段,不排具体先后,未定方向,无做的打算。
- **非 NTFS 边界维持关闭**(FAT32/exFAT/USB/网络盘)— 用户无场景,排除清单成立。
- **对标终点不设硬线**:P1/P2 后转反馈驱动维护期,G5 窗口切换/size:date 过滤等不预设,看实际使用反馈动态追加。
- **不设硬终点**:做完搜索收口不预设停止线,看实际使用反馈决定后续。

## 明确不做(边界维持)

- 非 NTFS 索引(无场景)
- 属性索引全量化(Everything 路线,内存代价大)
- memchr SIMD/倒排/trigram(留触发器,边际递减)
- 三进程并回(权限分离收益在)
- 剪贴板历史/内容索引/HTTP API/DLL 插件(定位选择)
- Windows 10/ARM/x86(明确排除)
- 多模态大模型理解图片(密钥/隐私/费用/网络依赖,违背"薄")
- 开放插件平台(先走内置 handler,等真有第三方想接再考虑)
